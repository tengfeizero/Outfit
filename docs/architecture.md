# 架构与选型

这份文档回答两个问题：**它是怎么运转的**，以及**为什么有些常见的做法我没用**。

---

## 1. 全貌

```
┌──────────────┐        手机/电脑浏览器（局域网）
│  React 前端   │◄──────────────────────────────┐
└──────────────┘                               │
                                               │
┌──────────────────────────────────────────────┴─────────┐
│  FastAPI（单进程，127.0.0.1 之外不可达）                  │
│                                                        │
│  ┌──────────────────────────────────────────────────┐  │
│  │ agent 循环（手写，~200 行）                         │  │
│  │                                                  │  │
│  │  用户一句话                                        │  │
│  │    ↓                                             │  │
│  │  调度器（LLM，JSON 动作）→ 工具 → 观察 → 再调度     │  │
│  │    ↑______________________|                       │  │
│  │   停止条件：finish / 6 步 / ¥1.2 / 2 张图           │  │
│  └──────────────────────────────────────────────────┘  │
│         │ 工具         │ 规则          │ 外部            │
│         ▼              ▼               ▼                │
│   天气 Open-Meteo   候选池+打分     混元打标/出图         │
│   衣橱检索          组套三套        （只有这两处花钱）     │
│                                                        │
│  SQLite：衣橱 / 档案 / 方案 / 运行轨迹 / 事件             │
│  文件：data/photos、cutouts、renders、models             │
└────────────────────────────────────────────────────────┘
```

一句话概括设计：**模型只负责"看图"和"画图"，所有"判断"都是确定性代码。**
候选池、正式度映射、配色、预算、降级——都不经过模型。这是可解释性的来源。

## 2. agent 循环拆成六块

| # | 部件 | 在哪 | 干什么 |
|---|---|---|---|
| 1 | 工具注册表 | `agent/tools.py` | 5 个工具，每个带 JSON schema 和成本估价 |
| 2 | 状态 | `agent/loop.py` 的 `state` dict | 天气、候选、方案、已出的图，工具之间靠它传话 |
| 3 | 调度 | `clients/tokenhub.decide_action` | 看轨迹，输出 `{thought, action, args}` |
| 4 | 执行 | `_Runner.execute` | 校验动作、调工具、异常转成 observation，不中断循环 |
| 5 | 停止条件 | `over_budget` / `finish` / `max_steps` | 三种刹车，缺一个都会烧钱 |
| 6 | 轨迹 | `agent_run` 表 | 每步的 thought / 参数 / 结果 / 耗时 / 花费 |

### 工具

| 工具 | 输入 | 输出 | 成本 |
|---|---|---|---|
| `get_weather` | — | 出门温度、天气 | 免费 |
| `search_wardrobe` | 场合、温度、正式度区间 | 可穿单品 + 是否凑得齐 | 免费 |
| `compose_outfit` | 场合、温度 | 三套方案 | ¥0.01 |
| `render_outfit` | 方案序号 | 试穿图（含校验） | ¥0.35 |
| `finish` | 一句总结 | — | 免费 |

### 停止条件

- `finish`：模型自己说结束
- 6 步：防止原地打转
- ¥1.2 或 2 张图：防止一次请求把额度烧光
- 连续 2 个不存在的工具：模型明显跑偏，直接收

## 3. 失败时会发生什么

这是 agent 和 demo 的分界线。每个失败都有定义好的行为，没有一个是"报错给用户看"。

| 失败 | 行为 |
|---|---|
| 模型返回的不是 JSON | 修全角引号 → 重压成 JSON → 再失败就带上原文重问一次 |
| 调度器连续失手 | **编排器接管**：用固定流程补出方案，状态记 `degraded` |
| 工具内部抛异常 | 转成 observation 回给模型，循环继续（模型能看到错误并换策略） |
| 出图不像本人 | 视觉校验不过 → 缩减参考图重试一次 → 仍不过 → 退回搭配板 |
| 超出预算 | 立刻 finish，已出的图保留 |
| 没有配置模型 | 整体退化成确定性流程，轨迹照样记录，状态记 `fallback` |

`degraded` 和 `fallback` 这两个状态是刻意保留的：**降级不是失败，但要留痕**，否则你永远不知道有多少请求其实没走成 agent。

## 4. 为什么不用 agent 框架

这是被问得最多的一个问题，所以正面回答。

**规模不匹配。** 5 个工具、单层循环、无多 agent 协作、无人在环审批。这个体量下，LangGraph 的 StateGraph 要你先把状态定义成 TypedDict、画节点、连条件边——手写 200 行的事，用框架约 400 行 + 一个重依赖。

**刹车得自己写。** 步数、预算、图片张数这些限制，框架基本不管。真正防止烧钱的代码，用不用框架都得自己写。

**调试成本是实打实的。** 出问题时我要一眼看到"第 3 步模型选了 A 而不是 B"，手写循环直接打印轨迹数组。框架的抽象层会让这个动作变慢。

**可测试性反而更好。** 手写循环可以用一个脚本化的假模型驱动，13 个测试覆盖了：正常多步、非法工具、连续非法、步数超限、模型崩溃、无模型降级、轨迹结构。换成框架，这些测试要么变重，要么得依赖框架的测试工具。

### 但如果要往上长，会换成什么

| 需求 | 现在怎么做 | 会换成什么 |
|---|---|---|
| 多 agent 协作（搭配师 + 买手 + 尺码顾问） | 做不到 | LangGraph 的多节点图 |
| 人在环审批（出图前先给你确认） | 前端按钮代替 | 框架的 interrupt / checkpoint |
| 长任务断点续跑 | 不支持 | LangGraph checkpoint + 持久化 |
| 轨迹可视化 | 自己写的前端面板 | LangSmith / Langfuse |

**工具层不用动。** `TOOLS` 是普通的「名字 + schema + 函数」，迁到任何框架都是同一个形状——这也是我刻意没把工具写成某个框架的装饰器的原因。

### 概念对应（被问到时能对上号）

| 手写的 | LangGraph 里 |
|---|---|
| `TOOLS` 字典 + schema | `@tool` / function calling |
| `with_model()` 的 for 循环 | `StateGraph` 的条件边 |
| `state` dict | State + checkpoint |
| `Step` 列表 → `agent_run.steps` | LangSmith trace |
| `MAX_STEPS` / `MAX_COST` | 没有对应物，自己加 |
| 调度失手 → 编排器接管 | supervisor / fallback node |

## 5. 一个刻意的取舍：模型做判断 vs 代码做判断

候选池的硬过滤（12 月不能出现短袖）、正式度映射、配色打分、每日限额——全部是代码。

为什么不让模型判断：**这些是"能不能"，不是"好不好"。** 模型会说"这件短袖配大衣很好看"，那是审美；但 5℃ 穿短袖是物理问题，不该有讨论空间。规则错了能追到一行代码，模型错了只能重跑。

模型只做两件它明显更强的事：看照片认衣服、按几件衣服画出上身效果。
